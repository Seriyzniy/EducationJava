Одна из ключевых проблем при работе с векторными хранилищами — это работа с данными, которые регулярно изменяются, потому что изменения означают переиндексацию. 

А **переиндексация может привести к дорогостоящим перевычислениям встраиваний и дублированию** уже существующего контента.

К счастью, **LangChain предоставляет API индексации**, *который упрощает синхронизацию ваших документов с векторным хранилищем*. 

API использует класс (`RecordManager`) **для отслеживания записи документов в векторное хранилище**

При ==индексации контента для каждого документа ВЫЧИСЛЯЮТСЯ ХЕШИ== и в **RecordManager сохраняется следующая информация**:

- Хэш документа (хэш как содержимого страницы, так и метаданных)
    
- Время записи
    
- ID источника (каждый документ должен включать информацию в свои метаданные для определения конечного источника этого документа)

Кроме того, API индексации предоставляет режимы очистки (cleanup modes), чтобы помочь вам решить, как удалять существующие документы в векторном хранилище. 
> Например, *если вы внесли изменения в способ обработки документов перед вставкой или если исходные документы изменились*, **вы можете удалить все существующие документы, которые происходят из того же источника, что и новые индексируемые документы.** 
> 
> Если некоторые исходные документы были удалены, вы захотите удалить все существующие документы в векторном хранилище и заменить их переиндексированными документами.

Режимы следующие:

- Режим **None** не выполняет автоматической очистки, позволяя пользователю вручную выполнять очистку старого контента.
    
- Режимы **Incremental** и **full** удаляют предыдущие версии контента, если содержимое исходного документа или производных документов изменилось.
    
- Режим **Full** дополнительно удаляет любые документы, не включенные в документы, индексируемые в данный момент.


Вот пример использования API индексации с базой данных Postgres, настроенной как менеджер записей:

**Python**
```python
from langchain.indexes import SQLRecordManager, index
from langchain_postgres.vectorstores import PGVector
from langchain_openai import OpenAIEmbeddings
from langchain.docstore.document import Document

connection = "postgresql+psycopg://langchain:langchain@localhost:6024/langchain"

collection_name = "my_docs"

embeddings_model = OpenAIEmbeddings(model="text-embedding-3-small")

namespace = "my_docs_namespace"

vectorstore = PGVector(
    embeddings=embeddings_model,
    collection_name=collection_name,
    connection=connection,
    use_jsonb=True,
)
record_manager = SQLRecordManager(
    namespace,
    db_url=
    "postgresql+psycopg://langchain:langchain@localhost:6024/langchain"
)

# Создание схемы, если она не существует
record_manager.create_schema()

# Создание документов
docs = [
    Document(
	    page_content='there are cats in the pond', 
	    metadata={"id": 1, "source": "cats.txt"}),
    Document(
	    page_content='ducks are also found in the pond', 
	    metadata={"id": 2, "source": "ducks.txt"}),
]

# Индексация документов
index_1 = index(
    docs,
    record_manager,
    vectorstore,
    cleanup="incremental",  # предотвращает дублирование документов
    source_id_key="source",  # использует поле source из метаданных
)
print("Index attempt 1:", index_1)

# второй раз при попытке индексации не будет добавлено ничего нового
index_2 = index(
    docs,
    record_manager,
    vectorstore,
    cleanup="incremental",
    source_id_key="source",
)
print("Index attempt 2:", index_2)

# Если мы изменяем документ, новая версия будет добавлена, а старые
# версии с тем же источником будут удалены
docs[0].page_content = "I just modified this document"

index_3 = index(
    docs,
    record_manager,
    vectorstore,
    cleanup="incremental",
    source_id_key="source",
)
print("Index attempt 3:", index_3)
```

Сначала **вы создаете менеджер записей, который отслеживает, какие документы были проиндексированы ранее**. 

Затем вы **используете функцию `index` для синхронизации вашего векторного хранилища** с новым списком документов. 

В этом примере мы используем режим incremental, поэтому любые документы с тем же ID, что и предыдущие, будут заменены новой версией.

## Оптимизация индексации

Базовый этап индексации RAG включает наивное разбиение текста и встраивание фрагментов данного документа. 

Однако этот *базовый подход приводит к несогласованным результатам поиска и относительно высокому уровню галлюцинаций, особенно когда источник данных содержит изображения и таблицы.*

Существуют различные стратегии повышения точности и производительности этапа индексации. 
В следующих разделах мы рассмотрим три из них: MultiVectorRetriever, RAPTOR и ColBERT.

### MultiVectorRetriever

*Документ, содержащий смесь текста и таблиц*, **не может быть просто разбит по тексту на фрагменты и использован как контекст в виде встраиваний**: ***вся таблица может быть легко потеряна.***

Чтобы решить эту проблему, мы можем разделить документы, которые мы хотим использовать для синтеза ответа, от ссылки, которую мы хотим использовать для поисковика. **Рисунок 2-5** иллюстрирует это.

![[Pasted image 20260712130116.png]]
**Рисунок 2-5. Индексация множественных представлений одного документа**

*Например, в случае документа, содержащего таблицы*, мы можем сначала сгенерировать и встроить сводки элементов таблицы, гарантируя, что каждая сводка содержит ссылку `id` на полную исходную таблицу. 

Затем мы сохраняем исходные таблицы, на которые есть ссылки, в отдельном хранилище документов (docstore). Наконец, когда запрос пользователя извлекает сводку таблицы, мы передаем всю исходную таблицу, на которую есть ссылка, в качестве контекста в итоговый запрос, отправляемый LLM для синтеза ответа. Этот подход позволяет нам предоставить модели полный контекст информации, необходимой для ответа на вопрос.

Вот пример. Сначала давайте используем LLM для генерации сводок документов:

**Python**
```python
from langchain_community.document_loaders import TextLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_openai import OpenAIEmbeddings
from langchain_postgres.vectorstores import PGVector
from langchain_core.output_parsers import StrOutputParser
from langchain_core.prompts import ChatPromptTemplate
from pydantic import BaseModel
from langchain_core.runnables import RunnablePassthrough
from langchain_openai import ChatOpenAI
from langchain_core.documents import Document
from langchain.retrievers.multi_vector import MultiVectorRetriever
from langchain.storage import InMemoryStore
import uuid

connection = "postgresql+psycopg://langchain:langchain@localhost:6024/langchain"

collection_name = "summaries"

embeddings_model = OpenAIEmbeddings()

# Загрузка документа
loader = TextLoader("./test.txt", encoding="utf-8")
docs = loader.load()
print("length of loaded docs: ", len(docs[0].page_content))

# Разбиение документа
splitter = RecursiveCharacterTextSplitter(
	chunk_size=10000, 
	chunk_overlap=20)
chunks = splitter.split_documents(docs)

# Создание цепочки для суммаризации
prompt_text = "Summarize the following document:\n\n{doc}"
prompt = ChatPromptTemplate.from_template(prompt_text)

llm = ChatOpenAI(temperature=0, model="gpt-3.5-turbo")

summarize_chain = 
	{"doc": lambda x: x.page_content} | prompt | llm | StrOutputParser()

# Пакетный запуск цепочки по фрагментам
summaries = summarize_chain.batch(chunks, {"max_concurrency": 5})
```

Далее определим векторное хранилище и хранилище документов для хранения исходных документов и их встраиваний:

**Python**
```python
# Векторное хранилище для индексации фрагментов-сводок
vectorstore = PGVector(
    embeddings=embeddings_model,
    collection_name=collection_name,
    connection=connection,
    use_jsonb=True,
)

# Слой хранения для родительских документов
store = InMemoryStore()
id_key = "doc_id"

# Индексация сводок в векторном хранилище, которые ссылаются на
# родительские документы в хранилище документов:
retriever = MultiVectorRetriever(
    vectorstore=vectorstore,
    docstore=store,
    id_key=id_key,
)

doc_ids = [str(uuid.uuid4()) for _ in chunks]

# Каждая сводка связана с исходным документом через ID
summary_docs = [
    Document(page_content=s, metadata={id_key: doc_ids[i]})
    for i, s in enumerate(summaries)
]

# Добавление сводок документов в векторное хранилище
retriever.vectorstore.add_documents(summary_docs)

# Сохранение исходных документов в хранилище документов с использованием doc_ids
retriever.docstore.mset(list(zip(doc_ids, chunks)))
```

Наконец, давайте извлечем релевантный документ с полным контекстом на основе запроса:

**Python**
```python
# Векторное хранилище извлекает сводки
sub_docs = retriever.vectorstore.similarity_search("chapter on philosophy", k=2)

# Тогда как поисковик вернет более крупные исходные документы
retrieved_docs = retriever.invoke("chapter on philosophy")
```

### RAPTOR

RAPTOR (Recursive Abstractive Processing for Tree Organized Retrieval) — это техника, которая строит иерархическое дерево из фрагментов документа. Она работает следующим образом:

1. Документ разбивается на маленькие фрагменты
    
2. Фрагменты группируются по семантическому сходству
    
3. Для каждой группы генерируется краткая сводка
    
4. Процесс повторяется рекурсивно, создавая дерево от самых детальных фрагментов до самых общих сводок

![[Pasted image 20260712130756.png]]

**Преимущества RAPTOR:**
- Позволяет находить информацию на разных уровнях детализации
    
- Улучшает понимание глобального контекста
    
- Снижает количество галлюцинаций при работе с большими документами

### ColBERT

Одна из проблем использования моделей встраиваний на этапе индексации заключается в том, что они сжимают текст в векторные представления фиксированной длины, которые захватывают семантическое содержание документа. Хотя это сжатие полезно для поиска, встраивание нерелевантного или избыточного контента может привести к галлюцинациям в итоговом выводе LLM.

Одно из решений этой проблемы заключается в следующем:

1. Генерация контекстуальных встраиваний для каждого токена в документе и запросе.
    
2. Вычисление и оценка сходства между каждым токеном запроса и всеми токенами документа.
    
3. Суммирование максимальной оценки сходства каждого встраивания запроса с любым из встраиваний документа для получения оценки для каждого документа.
    

Это приводит к более детальному и эффективному подходу к встраиванию для лучшего поиска. К счастью, модель встраивания под названием ColBERT воплощает решение этой проблемы.

Вот как мы можем использовать ColBERT для оптимального встраивания наших данных:

**Python**
```python
# RAGatouille — это библиотека, которая упрощает использование ColBERT
# !pip install -U ragatouille
from ragatouille import RAGPretrainedModel
import requests

RAG = RAGPretrainedModel.from_pretrained("colbert-ir/colbertv2.0")

def get_wikipedia_page(title: str):
    """
    Получить полный текстовый контент страницы Википедии по её заголовку.
    :param title: str - Заголовок страницы Википедии
    :return: str - Полный текстовый контент страницы
    """
    # API-эндпоинт Википедии
    URL = "https://en.wikipedia.org/w/api.php"
    
    # Параметры для API-запроса
    params = {
        "action": "query",
        "format": "json",
        "titles": title,
        "prop": "extracts",
        "explaintext": True,
    }
    
    # Пользовательский заголовок User-Agent для соответствия политике Википедии
    headers = {"User-Agent": "RAGatouille_tutorial/1.0"}
    
    response = requests.get(URL, params=params, headers=headers)
    data = response.json()
    
    # Извлечение содержимого страницы
    page = next(iter(data["query"]["pages"].values()))
    return page["extract"] if "extract" in page else ""
    
full_document = get_wikipedia_page("Hayao_Miyazaki")

## Создание индекса
RAG.index(
    collection=[full_document],
    index_name="Miyazaki-123",
    max_document_length=180,
    split_documents=True,
)
# Запрос
results = RAG.search("What animation studio did Miyazaki work with?", k=5)

# Использование LangChain поисковика
retriever = RAG.as_langchain_retriever(k=3)
retriever.invoke("What animation studio did Miyazaki work with?")
```

Используя ColBERT, вы можете улучшить релевантность извлеченных документов, используемых в качестве контекста LLM.

## Что происходит под капотом ColBERT?

ColBERT (Contextualized Late Interaction over BERT) использует двухступенчатый подход:

**1. Создание встраиваний на уровне токенов**
В отличие от *традиционных моделей, которые создают одно встраивание для всего документа*, ***ColBERT создает отдельное встраивание для каждого токена***. Это позволяет сохранить более детальную информацию.

**2. Позднее взаимодействие (Late Interaction)**

Вместо вычисления сходства между двумя векторами фиксированной длины, ColBERT вычисляет сходство на уровне токенов:
```text
Для каждого токена запроса:
    Найти наиболее похожий токен документа
    Записать оценку сходства
Суммировать все оценки
```

**Преимущества ColBERT:**

|Аспект|Традиционные встраивания|ColBERT|
|---|---|---|
|Уровень детализации|Документ в целом|Каждый токен|
|Сжатие|Сильное (весь документ → 1 вектор)|Мягкое (каждый токен → вектор)|
|Потеря информации|Высокая|Низкая|
|Скорость поиска|Быстрая|Средняя|
|Точность|Средняя|Высокая|

## Индексирование с ColBERT

Процесс индексации с ColBERT включает следующие шаги:

1. **Разбиение на токены** — документ разбивается на токены
    
2. **Создание контекстуальных встраиваний** — каждый токен преобразуется во встраивание с учетом контекста
    
3. **Сжатие** — встраивания сжимаются для эффективного хранения
    
4. **Индексация** — сжатые встраивания сохраняются с идентификаторами токенов
    

Этот процесс занимает больше времени и ресурсов, чем традиционное встраивание, но обеспечивает значительно лучшие результаты поиска.

## Выбор стратегии индексации

|Стратегия|Когда использовать|Преимущества|Недостатки|
|---|---|---|---|
|Обычное разбиение|Простые текстовые документы|Простота, низкая стоимость|Потеря контекста таблиц и изображений|
|MultiVectorRetriever|Документы с таблицами и структурированными данными|Сохранение полного контекста|Увеличенная сложность, больше токенов|
|RAPTOR|Очень большие документы|Поиск на разных уровнях детализации|Высокая вычислительная сложность|
|ColBERT|Высокоточный поиск|Точность на уровне токенов|Больше требований к памяти|
