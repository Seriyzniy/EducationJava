Начнем с рассмотрения **традиционного метода** автоматизации тестов в Selenium. Этот подход, часто считающийся основой тестирования в Selenium, ***предполагает прямое взаимодействие с веб-элементами через явные локаторы и действия.*** Хотя это фундаментальная стратегия, ее масштабируемость и поддерживаемость в сложных и постоянно меняющихся средах — предмет для обсуждения.
(**НЕ УДОБНАЯ МАСШТАБИРУЕМОСТЬ**)


> [!NOTE] POM - страницы, элементы как отдельные классы
> Далее мы рассмотрим **Page Object Model (POM)** — структурный **паттерн проектирования**, который ***инкапсулирует свойства и поведение веб-страниц в отдельные классы.*** 

POM продвигает более модульный и объектно-ориентированный подход к созданию тестовых скриптов, решая многие проблемы традиционного метода, особенно связанные с поддерживаемостью и переиспользованием кода.

На основе POM вводится **Page Factory** — оптимизированная реализация, предоставляемая библиотекой поддержки Selenium. 
Благодаря **конфигурации на основе аннотаций, Page Factory улучшает POM**, предлагая более лаконичный и интуитивно понятный способ инициализации веб-элементов. В этом разделе рассматриваются синтаксис, использование, практические преимущества и ограничения в различных сценариях тестирования.

---
## Традиционный подход (Conventional Approach) - ВСЕ ДАННЫЕ И ЛОКАТОРЫ В ОДНОМ СКРИПТЕ

*Традиционно автоматизированные тестовые скрипты* представляли собой **смесь локаторов элементов (ID, XPath), тестовых данных и команд действий (клик, ввод текста) в одном скрипте**. 

Этот подход, хотя и прямолинейный, становится громоздким и хрупким по мере усложнения приложений и расширения тестовых наборов.

Рассмотрим простую HTML-форму входа:

```html
<html>
<head><title>Страница входа</title></head>
<body>
    <form id="loginForm">
        <input type="text" id="username" />
        <input type="password" id="password" />
        <input type="submit" id="loginButton" />
    </form>
</body>
</html>
```

*В традиционном подходе* **тесты пишутся непосредственно в тестовом скрипте. Локаторы и операции над элементами находятся в одном методе.** 

Вот как может выглядеть простой тест входа:
```java
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.junit.Test;
public class TraditionalLoginTest {
    @Test
    public void testLogin() {
        WebDriver driver = new ChromeDriver();
        driver.get("http://www.example.com/login");
        
        driver.findElement(By.id("username")).sendKeys("user");
        driver
	        .findElement(
		        By.id("password")
		    )
		    .sendKeys("password");
	    
        driver.findElement(By.id("loginButton")).click();
        
        // Проверки и тестовая логика здесь
        driver.quit();
    }
}
```

В этом примере тест делает всё сам: открывает браузер, переходит на страницу, находит элементы, взаимодействует с ними и закрывает браузер.

## Что такое POM?

**Page Object Model (POM)** — это *паттерн проектирования*, *который поощряет модульный и поддерживаемый подход* к написанию тестовых скриптов в Selenium. 

В POM 
- **веб-страницы** представляются как классы**,** 
- а **элементы** на этих страницах — **как переменные в классе.** 

**Взаимодействие с этими элементами** инкапсулируется **в виде методов** внутри класса. Такая абстракция приводит к более чистому и понятному коду.

---
### Создание класса страницы (Page Class)

Сначала необходимо создать Java-класс, представляющий страницу входа. Этот **класс содержит локаторы и методы для взаимодействия.**

Для **каждой страницы** вашего приложения с**оздается Java-класс.** Файл сохраняется как `LoginPage.java`:

```java
import org.openqa.selenium.By;
import org.openqa.selenium.WebDriver;

public class LoginPage {
    private WebDriver driver;
    private By usernameLocator = By.id("username");
    private By passwordLocator = By.id("password");
    private By loginButtonLocator = By.id("loginButton");
    
    public LoginPage(WebDriver driver) {
        this.driver = driver;
    }
    public void enterUsername(String username) {
        driver.findElement(usernameLocator).sendKeys(username);
    }
    public void enterPassword(String password) {
        driver.findElement(passwordLocator).sendKeys(password);
    }
    public void clickLogin() {
        driver.findElement(loginButtonLocator).click();
    }
}
```

**Структура `LoginPage.java`:**
- **Локаторы** — переменные (например, `usernameLocator`) для поиска элементов на странице.
    
- **Конструктор** — инициализирует WebDriver.
    
- **Методы** — `enterUsername`, `enterPassword`, `clickLogin` — взаимодействуют с элементами.

---
### Создание тестовых скриптов с использованием Page Object

Вместо того чтобы писать шаги теста напрямую в тестовом методе, **используем методы из объекта страницы** в файле `LoginTest.java`:

```java
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.junit.Test;
public class LoginTest {
    @Test
    public void shouldLoginSuccessfully() {
        WebDriver driver = new ChromeDriver();
        driver.get("http://www.example.com/login");
        
        LoginPage loginPage = new LoginPage(driver);
        loginPage.enterUsername("testUser");
        loginPage.enterPassword("testPass");
        loginPage.clickLogin();
        
        // Проверки и дальнейшая логика здесь
        
        driver.quit();
    }
}
```

`LoginTest.java` — это тестовый скрипт, который использует класс `LoginPage`. Он переходит на страницу входа, взаимодействует с ней через объект страницы и выполняет проверки.

---
## Основные файлы в POM
- **`LoginPage.java`** — представляет **страницу входа и содержит методы для взаимодействия с ее элементами.**
    
- **`LoginTest.java`** — содержит **тестовые скрипты**, использующие `LoginPage` для выполнения тестов.


> **В реальном проекте** у вас будет **Java-файл для каждой страницы** приложения и множество тестовых файлов, сгруппированных по функциям.

---
## Полный анализ создания POM

Основные шаги при создании POM:
1. **Анализ веб-страниц**: понять структуру каждой страницы, *определить все элементы для взаимодействия*.
    
2. **Проектирование классов страниц**: ***для каждой страницы** создать соответствующий **Java-класс***, который должен:
    - *Содержать локаторы для каждого элемента*.
        
    - *Предоставлять методы для действий* (клики, ввод текста, получение текста и т.д.).
        
3. **Инициализация WebDriver**: каждый ==объект страницы должен получить экземпляр WebDriver== (обычно через конструктор).
    
4. **Написание методов**: писать методы в классах страниц, выполняющие действия (например, вход в систему, заполнение форм). Эти методы абстрагируют сложность.
    
5. **Создание тестовых скриптов**: писать тесты, использующие методы объектов страниц. Тесты должны быть понятными и отражать действия пользователя.
    
6. **Обслуживание и обновление**: при изменении приложения обновляются только объекты страниц, что минимизирует влияние на тесты.

## Отличия традиционного подхода и POM

| Характеристика        | Традиционный подход                                                       | POM                                                          |
| --------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ |
| **Организация кода**  | Всё в одном месте. Скрипт напрямую взаимодействует с элементами.          | **Код организован в классы**, представляющие страницы.       |
| **Обслуживание**      | Изменения в UI требуют правок во всех скриптах, где используется элемент. | Изменения обычно ограничены классами страниц.                |
| **Переиспользование** | Код взаимодействия с элементом часто дублируется.                         | Один объект страницы можно использовать в нескольких тестах. |
| **Читаемость**        | Тесты становятся перегруженными и сложными для чтения.                    | Тесты читаются как высокоуровневое описание действий.        |
| **Масштабируемость**  | С ростом числа тестов управлять ими становится сложнее.                   | POM лучше масштабируется для больших проектов.               |

**Вывод**: хотя традиционный подход может быть быстрее для очень маленьких проектов, POM предлагает значительные преимущества для большинства сценариев, особенно по мере роста сложности.

---
## Лучшие практики POM

1. **Одна страница — один класс** — каждый класс представляет одну страницу или раздел страницы.
    
2. **Используйте осмысленные имена** — методы и локаторы должны иметь понятные имена.
    
3. **Используйте Page Factory** (рассмотрим ниже) — упрощает синтаксис инициализации.
    
4. **Скрывайте детали реализации** — инкапсулируйте внутренности страницы внутри объекта. Тесты не должны знать о локаторах.
    
5. **Не смешивайте проверки** — не помещайте проверки (assertions) в объекты страниц. Возвращайте значения и проверяйте их в тестах.
    
6. **Избегайте дублирования** — выносите повторяющийся код в общие методы.
    
7. **Используйте ожидания с умом** — используйте явные ожидания вместо жестких пауз (`Thread.sleep`).
    
8. **Держите код простым и сфокусированным** — каждый метод должен делать что-то одно.
    
9. **Рефакторинг** — регулярно пересматривайте и обновляйте объекты страниц.
    
10. **Документируйте код** — пишите комментарии к сложным или неочевидным частям.

## Page Factory

**Page Factory** — это ==вспомогательный класс Selenium==, который позволяет инициализировать веб-элементы более лаконично. 

Он **использует аннотации для идентификации элементов** и сокращает количество шаблонного кода.

Вместо `driver.findElement()` вы используете аннотацию `@FindBy` для объявления элементов на странице.

---
### Настройка Page Factory

**`LoginPage.java` с Page Factory:**

```java
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.support.FindBy;
import org.openqa.selenium.support.PageFactory;
public class LoginPage {
    
    @FindBy(id = "username")
    private WebElement usernameField;
    
    @FindBy(id = "password")
    private WebElement passwordField;
    
    @FindBy(id = "loginButton")
    private WebElement loginButton;
    public LoginPage(WebDriver driver) {
        PageFactory.initElements(driver, this);
    }
    public void enterUsername(String username) {
        usernameField.sendKeys(username);
    }
    public void enterPassword(String password) {
        passwordField.sendKeys(password);
    }
    public void clickLogin() {
        loginButton.click();
    }
}
```

**`DashboardPage.java` (после успешного входа):**

```java
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.WebElement;
import org.openqa.selenium.support.FindBy;
import org.openqa.selenium.support.PageFactory;

public class DashboardPage {
    
    @FindBy(id = "logoutButton")
    private WebElement logoutButton;
    
    public DashboardPage(WebDriver driver) {
        PageFactory.initElements(driver, this);
    }
    public void clickLogout() {
        logoutButton.click();
    }
}
```

**`LoginTest.java` с Page Factory:**
```java
import org.openqa.selenium.WebDriver;
import org.openqa.selenium.chrome.ChromeDriver;
import org.junit.Test;

public class LoginTest {
    @Test
    public void shouldLoginSuccessfully() {
        WebDriver driver = new ChromeDriver();
        driver.get("http://www.example.com/login");
        
        LoginPage loginPage = new LoginPage(driver);
        loginPage.enterUsername("ourUser");
        loginPage.enterPassword("ourPassword");
        
        loginPage.clickLogin();
        
        DashboardPage dashboardPage = new DashboardPage(driver);
        
        // Действия или проверки на странице Dashboard
        
        driver.quit();
    }
}
```

---
### Шаги для внедрения Page Factory

1. **Определите элементы** — определите элементы для взаимодействия.
    
2. **Создайте классы страниц** — используйте `@FindBy` для объявления элементов.
    
3. **Инициализируйте Page Factory** — ==в конструкторе вызовите== `PageFactory.initElements(driver, this);`.
    
4. **Напишите методы взаимодействия** — предоставьте методы для действий с элементами.
    
5. **Реализуйте тесты** — используйте объекты страниц в тестовых классах.
    

---
### Когда использовать Page Factory
- Когда в проекте много элементов для взаимодействия.
    
- Когда нужен более чистый и читаемый способ представления элементов.
    
- Когда команда знакома с паттерном и дополнительным уровнем абстракции.

---
### Отличия между POM и Page Factory

|Характеристика|POM|Page Factory|
|---|---|---|
|**Инициализация**|Обычно вручную через `driver.findElement()`|Автоматическая через `@FindBy` и `initElements()`|
|**Читаемость**|Может быть многословным|Более чистый код с аннотациями|
|**Инициализация элементов**|При создании объекта страницы|Ленивая (lazy) — элементы инициализируются при первом использовании|
|**Производительность**|Элементы инициализируются сразу|Ленивая загрузка может быть быстрее, если не все элементы используются|
|**Поддержка**|Хорошо документирован|Тоже хорошо поддерживается, но требует понимания POM|

---
### Лучшие практики Page Factory

- Используйте осмысленные имена для элементов.
    
- Используйте ленивую загрузку (элементы инициализируются при использовании).
    
- Сочетайте с принципами POM (один класс на страницу, методы отражают поведение).
    
- Следите за версиями Selenium — в новых версиях работа Page Factory может меняться.
    

---
## Ограничения POM и Page Factory

**Ограничения POM:**
- Требует значительных начальных усилий.
    
- Есть кривая обучения для новых команд.
    
- Поддержка большого количества страниц может быть сложной.
    
- Риск излишнего усложнения (over-engineering).
    

**Ограничения Page Factory:**
- Сложнее отлаживать из-за ленивой загрузки.
    
- Не подходит для страниц с динамическими элементами (меняющиеся атрибуты).
    
- Сильная зависимость от аннотаций.
    
- Потенциальные накладные расходы при частом обращении к одним и тем же элементам.
    

---
## Когда использовать POM или Page Factory?

**POM лучше выбирать, когда:**
- Приложение сложное, с множеством страниц.
    
- Проект долгосрочный и будет развиваться.
    
- Команда знакома с ООП.
    

**Page Factory лучше выбирать, когда:**
- Команда предпочитает конфигурацию на основе аннотаций.
    
- Важна читаемость тестового кода.
    
- Ленивая загрузка дает преимущество (не все элементы используются в каждом тесте).
    

**На практике** эти подходы часто используются вместе. Page Factory — это улучшение POM, обеспечивающее более эффективную инициализацию.

Для больших проектов лучше начинать с POM и добавлять Page Factory по мере необходимости. Для небольших проектов или команд, только начинающих автоматизацию, можно начать с POM, а затем внедрять Page Factory по мере роста проекта.
