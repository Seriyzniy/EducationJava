Представим, что ты хочешь использовать библиотеку для работы с OpenAI.

Без пакетного менеджера пришлось бы:

1. Скачать архив библиотеки.
2. Скачать все библиотеки, от которых она зависит.
3. Скачать библиотеки, от которых зависят эти библиотеки.
4. Разложить всё по нужным папкам.

Практически невозможно.

Поэтому существует **менеджер пакетов**.

Его задача:
- скачать библиотеку;
- скачать все её зависимости;
- установить их;
- обновлять;
- удалять;
- следить за версиями.

---
## Аналогия с Java
В Java этим занимается Maven.
```
pom.xml
↓
mvn install
↓
Maven скачал зависимости
↓
Проект готов к работе
```

В Python то же самое делает `uv`.
```
pyproject.toml
↓
uv sync
↓
uv скачал зависимости
↓
Проект готов
```

---
# 2. Из чего состоит Python-проект?

Современный Python-проект обычно выглядит так.
```
AI-Agent/
│
├── pyproject.toml
├── uv.lock
├── .venv/
├── app/
├── tests/
└── README.md
```

Каждый файл выполняет свою роль.

---
## pyproject.toml
Это главный конфигурационный файл проекта.
Практически аналог
```
pom.xml
```
или
```
build.gradle
```

В нем хранится информация:
- название проекта;
- версия;
- версия Python;
- зависимости.

Например
```
[project]
name = "ai-agent"

requires-python = ">=3.12"

dependencies = [
    "langchain",
    "openai"
]
```

Это означает
> Для работы проекта нужны библиотеки LangChain и OpenAI.

Но!
Здесь **не хранится информация о том, где физически находятся библиотеки**.

Только список необходимых зависимостей.

---
# 4. Что происходит при выполнении uv add?
Допустим
```
uv add langchain
```

Происходит несколько действий.
### Шаг 1
`uv` обращается в репозиторий PyPI.
```
PyPI
│
├── langchain
├── requests
├── numpy
└── ...
```

---
### Шаг 2
Находит библиотеку.

---
### Шаг 3
Смотрит её зависимости.
Например
```
LangChain
↓
langsmith
↓
requests
↓
urllib3
```

---
### Шаг 4
Скачивает всё дерево зависимостей.

---
### Шаг 5
Устанавливает библиотеки в виртуальное окружение.

---
### Шаг 6
Добавляет зависимость
в
```
pyproject.toml
```

---
### Шаг 7
Обновляет
```
uv.lock
```

То есть одной командой происходит довольно большая работа.

---
# 5. Что такое виртуальная среда (.venv)?
Представим.
Есть два проекта.
```
Project A
↓
LangChain 0.3
```
и
```
Project B
↓
LangChain 0.1
```

Если библиотеки были бы глобальными
```
Python
↓
LangChain ??
```
то проекты постоянно ломали бы друг друга.

---

Поэтому **каждый проект получает собственное окружение.**

```
Project A
│
├── .venv
│
└── pyproject.toml
```

```
Project B
│
├── .venv
│
└── pyproject.toml
```

Внутри `.venv` находится:
- собственный Python;
- собственные библиотеки;
- собственные настройки.

То есть
> **виртуальная среда** — это ==полностью изолированный Python== именно для данного проекта.

# 6. Что такое uv.lock? - точные версии зависивостей
Очень важный файл.

Предположим
в `pyproject.toml`
написано
```
dependencies = [
    "langchain"
]
```

Но существует множество версий.
```
0.2

0.3

0.4

0.5
```

Какую устанавливать?

Если каждый разработчик установит разную,
получится
```
У меня работает.
↓
У коллеги нет.
```

Чтобы этого не произошло,
существует
```
uv.lock
```

Он хранит
**точные версии абсолютно всех библиотек.**

Например
```
langchain==0.3.26

langsmith==0.2.15

requests==2.32.4

urllib3==2.5.0
```

Теперь у всех разработчиков окружение одинаковое.

---
# 7. Почему pyproject.toml и uv.lock — разные файлы?

Это разные уровни информации.

## pyproject.toml
Отвечает на вопрос
> Что нужно проекту?
```
langchain

openai

fastapi
```

---
## uv.lock
Отвечает на вопрос
> Какие именно версии должны быть установлены?

```
langchain==0.3.26

langsmith==0.2.15

requests==2.32.4
```

---
# 8. Что делает uv sync?
Представим,
ты клонировал проект.
```
git clone ...
```

В проекте есть
```
pyproject.tomluv.lock
```

Но нет
```
.venv
```

Теперь выполняешь
```bash
uv sync
```

Что делает `uv`?
### 1.
Создает
```
.venv
```

---
### 2.
Читает
```
uv.lock
```

---
### 3.
Устанавливает именно те версии, которые записаны в lock-файле.

---
### 4.
Проект готов.

Поэтому обычно после
```
git clone
```

первая команда —
```
uv sync
```

---
# 9. Что делает uv run?

Вместо
```
python main.py
```

пишут
```
uv run main.py
```

Почему?

Потому что

`uv` сам
- активирует виртуальную среду;
- использует нужную версию Python;
- запускает программу.

Не нужно вручную активировать `.venv`.

# 10. Полный жизненный цикл проекта

Создание проекта
```
uv init ai-agent
```
↓
Создание структуры
```
pyproject.tomlmain.pyREADME.md
```
↓
Добавление библиотеки
```
uv add langchain
```
↓
Обновился
```
pyproject.toml
```
↓
Создался
```
uv.lock
```
↓
Установились библиотеки
```
.venv
```
↓
Запуск
```
uv run main.py
```
↓
Git Commit
```
pyproject.tomluv.lock
```
↓
Другой разработчик
```
git clone
```
↓
```
uv sync
```
↓
Проект запускается без дополнительных настроек.

# 11. Что коммитится в Git?
Всегда
```
✅ pyproject.toml
✅ uv.lock
```

Никогда
```
❌ .venv❌ __pycache__
```

Почему?
Потому что
```
.venv
```

можно полностью восстановить командой
```
uv sync
```

# 12. Основные команды `uv`

|Команда|Назначение|Аналог в Maven|
|---|---|---|
|`uv init`|Создать новый проект|Создание Maven-проекта|
|`uv add <package>`|Добавить зависимость|Добавить `<dependency>`|
|`uv remove <package>`|Удалить зависимость|Удалить `<dependency>`|
|`uv sync`|Создать `.venv` и установить все зависимости|`mvn install` (по смыслу)|
|`uv run main.py`|Запустить проект|`mvn exec:java` / запуск из IDE|
|`uv lock`|Обновить lock-файл|Фиксация версий зависимостей|
